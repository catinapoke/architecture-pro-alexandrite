# Мотивация

Мониторинг требуется компании поскольку это обеспечивает быстрое нахождение источника проблем и реагирование на проблемы до получения обратной связи от клиентов и бизнеса. 

Сейчас у компании есть проблемы 
- с потерями заказов, которые не были решены за продолжительное время и 
- с обнаружением причин проблем при разработке
- со скоростью работы главной страницей MES

Мониторинг может помочь с определением размера нагрузки, пропускной способностью системы. 

# Выбор подхода к мониторингу

* Для всех метрик помимо указанных label добавляются label=env, который будет указывать к какому окружению относятся метрики.

На диаграмме системы компании представлено три контейнера API. Для такой ситуации хорошо подойдет подход "Четыре золотых сигнала" и добавил бы RPS из RED, чтобы яснее понимать нагрузку и способность ее обработки.

Т.е. метрики
- RPS (с label=uri)
- Latency (с label=uri и с графиками по разным персентилям)
- Errors - по запросам к ручкам (label=http_code и uri)
- Трафик(с label=type(in/out))
- Насыщенность - cpu utilization и memory по контейнерами (label=app и container_name)

Для баз данных выбрал бы следующие метрики (RED + "Четыре золотых сигнала")
- Насыщенность - cpu utilization и disk utilization
- Requests Rate — частота запросов к БД (с label = service, db_name)
- Latency - длительность самых долгих транзакций
    * Для детализации определенных запросов можно добавить label=query. Это может помочь с отладкой работы главной страницы MSE. Однако это можно сделать и на основе работы трейсов.
- Errors - ошибки по разным категориям (label = error_code)
- Трафик(с label=type(in/out))
- Количество соединений

Это покажет все самые важные параметры при работе с базой данных. 


А для Message Broker можно использовать "Четыре золотых сигнала".

Насыщенность в виде длины очереди - сигнал о работе сервисов потребителей.
Трафик напрямую влияет на работоспособность системы, хорошим решением будет показать лимит пропускной способности по трафику, чтобы понимать когда может потребоваться масштабирование заранее. 
Задержка и ошибки также важны для понимания состояния системы.

Метрики:
- inbound messages (label=queue)
- outbound messages (label=queue и consumer)
- Лаги в очередях (label=queue и consumer)
- Самое старое сообщение в каждое очереди (label=queue)

- Трафик(с label=type(in/out))
- produce latency p99
- consume latency p99
- Насыщенность - cpu utilization, memory и disk utilization по инстансам (label=instance)
- Produce errors
- Consume errors

Так мы увидим нагрузку, работу сервисов потребителей, работу брокера и возможные причины такой работы.

Для определения проблем в данных можно дополнительно собирать бизнес-метрики. Это поможет выявлять проблемные заказы раньше. Для сбора этих метрик желательно использовать реплику, чтобы по минимуму влиять на работу основного приложения.
Например:
- Количество заказов в разных статусах (label=status)
- Количество заказов в определенном статус выше SLA (label=status, age)

Для фронтенда я бы собирал базовые Web Vitals, crash rate, размер бандла и ошибки. Это можно сделать через Sentry или Appmetrica. 

Для s3 хранилища:
- Disk utilization
- Latency (с label=file)
- http errors (с label=http_code)
- Трафик(с label=type(in/out))


## Работа с метриками насыщенности

Для каждого показателя насыщенности должна быть зафиксирована верхняя планка - в идеале с запасом от стандартного нормального использования на 40%, либо от физических ограничений в виде пропускной способности диска, количество ядер процессора, количества оперативной памяти в системе или возможностей маршрутизатора. 

В приближении к ограничению на 15% (т.е. показатель 85% от максимума) необходимо алармить в чат DevOps инженера с тегом. Частота проверки должна быть раз в 5 минут. Т.к. он один то он должен определить величину проблемы и если она быстро решается то решить на месте, если нет, то завести себе тикет на себя или команду отвечающую за сервис. 

# План действий

Для мониторинга требуется поднять time-series базу данных для хранения показателей - например Grafana Mimir поскольку он open-source и хорошо поддерживается Grafana, которую можно использовать для визуализации показателей. 

Для сборки показателей можно использовать Prometheus/OpenTelemetry Collector и стандартные exporter'ы для RabbbitMQ, postgresql, nginx, JVM exporter, .net exporter и docker/kubernetes. Если части метрик не хватает, то можно дополнительно создать кастомные метрики для приложений и собирать их. 

На основе этих метрик далее стоит определить набор граничных состояний и выставить для них алерты. Для каждого алерта описать документацию и правила реагирования с тегом ответственных.
